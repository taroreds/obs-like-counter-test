# Architecture and Product Decisions

この文書は、高評価ゴール OBSウィジェットの開発において採用した判断、理由、却下した案、既知の制約を記録する。

実装方法だけでなく、「なぜその構成にしたか」を後から確認できるようにすることを目的とする。

この文書に記載された決定は、将来のAPI連携、設定支援クライアント、管理アプリ等の設計時に再検討される可能性がある。ただし、変更する場合は、従来の判断理由と移行上の影響を確認する。

---

## 決定状態

各項目では、次の状態を使用する。

- `採用`
  - 現在の正式な設計・仕様として使用している。
- `保留`
  - 将来の判断材料はあるが、現時点では確定していない。
- `却下`
  - 現在の要件や制約には適さないため採用しなかった。
- `将来再検討`
  - 現時点では実装しないが、要件が変われば再評価する。
- `正式対応外`
  - 技術的には動作しうるが、サポート対象に含めない。

状態は決定そのものの状態だけを示す。実施状況や適用範囲を区別する必要がある場合は、
状態の直下へ次を併記する。

- `**適用範囲:**` 方針のみ確定。具体仕様は未確定
- `**実施状況:**` 実施済み / 未実施

# 1. 基本方針

## D-001: 現行ウィジェットはHTML・CSS・JavaScriptだけで構成する

**状態:** 採用

### 決定

現行の表示ウィジェットとOBSカスタムブラウザドックは、通常のHTML・CSS・JavaScriptだけで構成する。

現時点では、次を導入しない。

- Node.js
- npm
- ビルドツール
- ES Modules
- 外部JavaScriptライブラリ
- 外部フォント
- Webサーバー
- OBS WebSocket

### 理由

- ZIPを展開して使用できる軽量な構成を維持できる。
- 開発環境と配布物の差を小さくできる。
- 外部依存関係の更新、脆弱性、互換性問題を減らせる。
- 利用者にNode.js等の実行環境を導入させずに済む。
- 問題発生時の切り分け対象を限定できる。
- 初期段階では、高度なフレームワークを必要とする規模ではない。

### 却下した案

- React、Vue等のUIフレームワーク
- npmパッケージを利用する構成
- TypeScriptとバンドラーを使用する構成
- 開発用Webサーバーを製品の必須要件にする構成

### 影響

- JavaScriptファイル間の依存順序を`script`の読み込み順で管理する必要がある。
- 名前空間は`window.LIKE_GOAL`を使用する。
- モジュール境界は言語機能ではなく、ファイル責務と公開APIによって維持する。
- 将来、管理アプリやAPI連携を実装する場合、この制約を維持するかは別途判断する。

## D-002: デザイン競争ではなく、技術的な運用価値を重視する

**状態:** 採用

### 決定

本製品は、多数の装飾テーマや高度なビジュアル表現を主な差別化要素としない。

次の価値を優先する。

- 状態管理の堅牢性
- 自動取得
- 手動フォールバック
- 永続化
- 入力検証
- 接続診断
- 障害時の縮退動作
- 設定作業の簡略化
- 導入時のミス防止

### 理由

開発方針と開発者の強みが、デザイン制作よりもプログラミング、システム設計、障害対応、保守性にあるため。

市場には、見た目を主な価値とするOBS素材・ウィジェットが多数存在する。そこで同じ競争をするより、配信者の操作負担や設定ミス、API障害、状態消失などを技術的に解決する方が適している。

### 却下した案

- テーマ数を増やすことを最優先する
- 装飾・アニメーションだけで商品価値を作る
- デザインバリエーションを主な価格根拠にする

### 影響

表示テーマは最低限に留める可能性がある。

将来の商品価値は、API連携、設定支援、運用支援、フォールバック等と組み合わせて形成する。

## D-036: 複数ウィジェット間での共通コード共有方式

**状態:** 保留

### 背景

リポジトリは `obs-tool-lab/` 配下にウィジェット単位で作成する。今後、別のOBS
ウィジェットを同じ基盤から開発する予定がある。

しかしD-001によりNode.js・npm・ビルド・ES Modulesを使用しないため、リポジトリを
またいだコード共有の手段が存在しない。`state.js`、`transport.js`、`persistence.js`、
`render.js` は各リポジトリへコピーされることになる。

### 論点

コピー方式では、次が起きる。

* 各コピーが独立に修正され、時間とともに分岐する
* 一方で見つかったバグの修正が他へ伝播しない
* 「共通基盤」が実体を持たず、初期テンプレートに退化する

### 選択肢

| 案 | 内容 | 代償 |
| --- | --- | --- |
| コピー容認 | 基盤を「出発点」と割り切る | 分岐が前提。修正の横展開は手作業 |
| モノレポ | `obs-tool-lab` を1リポジトリ化し `shared/` を置く | 現行のリポジトリ分割方針と異なる。配布物切り出し手順が必要 |
| ビルド導入 | D-001を変更し共有モジュールを結合する | AGENTS.mdの必須制約に抵触。§13の変更手順が必要 |

### 判断時期

2つ目のウィジェットへ着手する前。分岐したコピーを後から統合するコストは、
先に決めるコストより高い。

### 関連

D-001、D-016、D-020

---

## D-037: 通信プロトコルの定数を `protocol.js` へ集約する

**状態:** 採用

### 決定

BroadcastChannelのチャンネル名と、通信メッセージの `kind` 値（`state`、`action`、
`sync-request`）を `protocol.js` に定義し、`input-channel.js` と `controller.js` は
そこを参照する。

アクション種別（`increment` 等）は集約対象に含めない。

### 理由

チャンネル名とkind値は、表示側とcontrollerが一致していなければ通信が成立しない共有
語彙である。2ファイルへ重複して持つと、D-036で別ウィジェットへ派生させる際に片方
だけ変更する見落としが起きる。

その症状は「別ウィジェットのcontrollerが自分の表示ページを操作する」という形で現れる。
保存領域はパススコープで分離されるため（D-020）、この故障は通信側でだけ発生する。
非対称であることが原因特定を遅らせる。

アクション種別を含めないのは、D-007により `input-channel.js` の構造検証と `state.js` の
最終判定を意図的に分離しているためである。共通化すると2つの検証層が癒着する。また
`state.js` を共有ファイルへ依存させると、実行時状態の唯一の正本（D-003）という位置
づけと依存方向が逆転する。

### 却下した案

* `config.js` へチャンネル名を置く
  - `config.js` は表示内容の利用者設定であり、controllerが読む筋合いがない
  - 利用者の編集項目が増え、D-033の設定簡略化と逆行する
* `transport.js` に既定値を持たせる
  - `transport.js` は「プロトコルとDOMを扱わない」と定義済み（architecture.md §3）
* 定数を持たず、両ファイルへ重複を残す
  - 現状維持であり、D-036の派生時に見落としが起きる

### 影響

`index.html` と `controller.html` の両方で、`transport.js` より前に `protocol.js` を
読み込む。配布物に必須のファイルが1つ増えるため、`docs/test-plan.md` T-403（不足
ファイル）の対象が増える。

## D-038: 通信チャンネルのインスタンス分離を現時点では行わない

**状態:** 保留

### 背景

保存キーは `location.pathname` を含むため分離されるが、チャンネル名は固定である
（D-020）。配布フォルダをコピーして2つ同時にOBSへ登録すると、利用者は意図せず
D-016の非対応構成に入る。

### 技術的には解決できる

`location.pathname` のディレクトリ部分をチャンネル名へ含めれば、同じフォルダの2ページ
は同じチャンネル、別フォルダは別チャンネルになる。利用者による設定は不要である。
`index.html` と `controller.html` はファイル名が異なるため、フルパスは使えない。

### 現時点で採用しない理由

故障モードが悪化する。

* 現在の故障：コピーを2つ登録した利用者だけで混線する（D-016で正式対応外と宣言済み）
* 変更後の故障：Browser Sourceとドックのfile URLに、大文字小文字やエンコードの差が
  1文字でもあると通信が成立しない

後者は全利用者に起こりうる。さらにcontrollerは「同期待機」のまま停止し、現行では
診断情報を何も示さないため、利用者は原因を特定できない。

### 判断時期

controllerの接続診断（D-031の「導入診断」）を実装した後。診断がなければ、この変更は
利用者にとって原因不明の通信不能を増やすだけになる。

### 関連

D-016、D-020、D-031、D-037

---

## D-039: 別フォルダ間のBroadcastChannel混線は未測定である

**状態:** 保留

### 背景

D-020は、配布フォルダをコピーした場合に保存領域だけが分離され、通信チャンネルは共有されると記録している。

2026-08-02 の測定では、通常ブラウザで**同一フォルダ内**の `source.html` と `dock.html` の間で双方向通信が成立することを確認した。しかし**別フォルダ間**の通信は測定していない。

### 判断を保留する理由

同測定で、`location.origin` の表示値がオリジンの実体を反映しないことが分かった。通常ブラウザのコンソールには次のメッセージが出力された。

```text
'file:' URLs are treated as unique security origins.
```

`location.origin` は `file://` と表示されるが、Chromeの内部では file: URL ごとに一意のセキュリティオリジンとして扱われている。それでもBroadcastChannelが別URL間で成立したことから、BroadcastChannelやlocalStorageについては file:// を共通オリジンとして扱っているものと考えられる。

localStorageが file:// 間で共有されるからこそ、D-020でパススコープの保存キーが必要になったという経緯とも整合する。

したがって別フォルダ間でも混線する可能性は高いが、**根拠は「originの表示値が同じだから」ではなく「BroadcastChannelが別URL間で通ったから」である**。同一フォルダでの結果を別フォルダへそのまま外挿することはできない。

### 測定方法

配布フォルダをコピーし、2組の `source.html` と `dock.html` を同時に開いて、フォルダをまたいだPING/PONGが届くかを確認する。追加実装は不要である。

### 判断時期

D-038（通信チャンネルのインスタンス分離）を判断する時点。それまではD-016とD-020の記録で足りる。

### 関連

D-016、D-020、D-038

# 2. 状態管理

## D-003: `state.js`を実行時状態の唯一の正本とする

**状態:** 採用

### 決定

実行時のウィジェット状態は、`state.js`が管理するストアを唯一の正本とする。

controller、render、persistence、通信アダプターは、独自に別の正本を持たない。

### 理由

複数の場所が状態の正本になると、次の問題が起きる。

- 表示値とcontroller表示の不一致
- 保存値と実行時状態の不一致
- 更新順序による競合
- リセット処理の不整合
- API自動取得と手動操作の衝突

状態変更を`dispatch()`に集約することで、検証、正規化、通知、保存、描画を一貫して行える。

### 却下した案

- controller側で先に値を更新し、後から表示側へ送る
- persistence層がstate内部を直接書き換える
- render側がDOM表示値を状態として扱う
- config、controller、localStorageの各値を同格に扱う

### 影響

すべての実行時変更は、原則として既存アクションを通じて行う。

## D-004: `achieved`は保存せず、`current >= goal`から導出する

**状態:** 採用

### 決定

`achieved`は独立した状態として保存しない。

常に次の条件から計算する。

```javascript
current >= goal
````

### 理由

`achieved`を独立保存すると、次のような矛盾状態が生じ得る。

```javascript
{
  current: 120,
  goal: 100,
  achieved: false
}
```

導出可能な値を保存しないことで、状態の不整合を防止できる。

### 却下した案

* `achieved`をconfigへ保存する
* `achieved`をlocalStorageへ保存する
* controller側で達成状態を独自計算して正本とする

### 影響

snapshotには利便性のため`achieved`を含めるが、保存データには含めない。

---

## D-005: 公開状態APIは3種類に限定する

**状態:** 採用

### 決定

正式な外部公開APIは次の3つとする。

```javascript
window.LIKE_GOAL.getState()
window.LIKE_GOAL.dispatch(action)
window.LIKE_GOAL.subscribe(listener)
```

### 理由

* 状態の直接書き換えを防げる。
* 将来、内部実装を変更しても公開APIを維持しやすい。
* controller、通信アダプター、将来のAPI入力層を同じインターフェースへ接続できる。
* テスト対象を限定できる。

### 却下した案

* `window.LIKE_GOAL.state.current`のような直接参照・直接代入
* アクションごとに多数のグローバル関数を公開する
* state store自体をグローバルへ公開する

### 影響

`window.LIKE_GOAL.internal`以下の関数は内部用であり、正式な外部APIとは扱わない。

---

## D-006: snapshotは毎回新規作成し、freezeする

**状態:** 採用

### 決定

`getState()`と購読者へ渡すsnapshotは、毎回新しい平坦なオブジェクトを生成し、`Object.freeze()`する。

### 理由

外部コードがsnapshotを書き換えて、内部状態を変更したと誤認することを防ぐため。

参照共有による意図しない変更や、購読者間の干渉も避けられる。

### 却下した案

* 内部stateオブジェクトをそのまま返す
* 同じsnapshotオブジェクトを使い回す
* controllerへ可変オブジェクトを渡す

### 影響

snapshotは読み取り専用の時点情報として扱う。

---

## D-007: 数値の最終検証は`state.js`へ集約する

**状態:** 採用

### 決定

数値の正規化、切り捨て、範囲制限、有限値判定は`state.js`を正本とする。

`input-channel.js`では、通信メッセージの構造だけを検証する。

controller側では利用者向けの事前検証を行うが、最終判定は`dispatch()`へ委ねる。

### 理由

同じ数値仕様を複数ファイルへ実装すると、将来の変更時に規則が食い違う可能性がある。

例：

* controllerでは小数を拒否する
* stateでは小数を切り捨てる
* 通信アダプターでは数値文字列を拒否する

このような不整合を避けるため、最終規則はstateへ集約する。

### 却下した案

* controller、input-channel、stateで同じ数値変換を個別実装する
* 通信アダプターで値を正規化してからstateへ渡す
* controllerで正常と判断した値をstateでは無条件に受け入れる

### 影響

controllerの入力エラー表示はUX支援であり、セキュリティ境界や最終検証ではない。

# 3. 描画

## D-008: 状態管理とDOM描画を分離する

**状態:** 採用

### 決定

`state.js`はDOMを扱わず、`render.js`は状態変更ロジックを持たない。

### 理由

* 状態ロジックをDOMなしで確認できる。
* 将来表示デザインを変更してもstateへの影響を抑えられる。
* API取得やcontroller等の入力元を追加しやすい。
* 表示上の不具合と状態上の不具合を切り分けやすい。

### 却下した案

* `app.js`へ状態変更とDOM操作を集中させる
* ボタンイベント内で直接DOMを書き換える
* DOM表示値を読み取って次の状態を計算する

### 影響

DOM描画は`renderWidget()`へ集約する。

---

## D-009: 文字列の描画には`textContent`を使用する

**状態:** 採用

### 決定

ラベル、メッセージ、数値等の表示には`innerHTML`ではなく`textContent`を使用する。

### 理由

設定値や将来の外部データにHTMLが含まれても、意図しないタグやスクリプトとして解釈されないようにするため。

### 却下した案

* 設定値を`innerHTML`へ直接代入する
* メッセージ内で任意HTMLを許可する

### 影響

現時点ではリッチテキスト表示をサポートしない。

# 4. OBS操作と通信

## D-010: 表示ページと操作ページを分離する

**状態:** 採用

### 決定

配信映像へ表示する`index.html`と、OBS内で操作する`controller.html`を分離する。

### 理由

* 操作ボタンを配信映像へ映さずに済む。
* OBSカスタムブラウザドック内で操作を完結できる。
* 表示レイアウトと操作UIを独立して変更できる。
* controllerを閉じても表示側の状態を維持できる。

### 却下した案

* 表示ウィジェット自体に操作ボタンを配置する
* Browser Sourceの「操作」画面だけを正式な操作方法とする
* キーボードショートカットだけで操作する

### 影響

利用者はBrowser Sourceとカスタムブラウザドックの2つをOBSへ登録する。

---

## D-011: Browser Sourceとcontroller間にはBroadcastChannelを使用する

**状態:** 採用

### 決定

現行構成では、Browser Sourceとcontroller間の通信にBroadcastChannelを使用する。

チャンネル名は次とする。

```text
obs-like-goal-widget-v1
```

### 理由

* 外部サーバーなしでページ間通信ができる。
* 外部ライブラリを必要としない。
* controllerからactionを送り、表示側からstateを返す構造に適している。
* 技術スパイクでOBS上の双方向通信を確認できた。

### 検証結果

次の構成では通信できなかった。

```text
Browser Source:
「ローカルファイル」を有効

controller:
file:/// URL
```

次の構成では双方向通信に成功した。

```text
Browser Source:
「ローカルファイル」を無効
file:///.../index.htmlをURL欄へ指定

controller:
file:///.../controller.htmlを指定
```

### 原因

2026-08-02 の実機測定（OBS 32.2.2.1 / Windows 11 25H2）で、通信可否の違いは `location.origin` の不一致によるものと確認した。

| 環境 | location.origin | location.protocol |
| --- | --- | --- |
| カスタムブラウザドック | `file://` | `file:` |
| Browser Source（「ローカルファイル」有効） | `http://absolute` | `http:` |
| Browser Source（「ローカルファイル」無効、URL欄へfile URL） | `file://` | `file:` |

「ローカルファイル」を有効にすると、OBSは独自のスキームハンドラー経由で `http://absolute/C:/...` としてページを読み込む。ドックは常に `file://` であるため、両者のoriginが一致せずBroadcastChannelが成立しない。

この結果はOBS 32.2.2.1 でも再現しており、当初の検証時から挙動は変わっていない。

originはOBS再起動後も変化しなかった。

### 故障の性質

構成A（「ローカルファイル」有効）では、次のすべてが成功する。

* BroadcastChannelのチャンネル生成
* PING送信ボタンの操作
* 送信処理そのもの（例外もエラーも発生しない）

届かないのは受信側だけである。BroadcastChannelは送信先の存在を確認しないため、送信側からは正常に動作しているように見える。

利用者から見た症状は「操作はできるが数字が動かない」だけで、エラーメッセージもログも出ない。原因を推測する手がかりが何もない。

### 却下した案

* localStorageのstorageイベントによる通信
* OBS WebSocket
* ローカルHTTPサーバー
* ページ間でグローバルオブジェクトを直接共有する方式

### 影響

READMEには、Browser Sourceの「ローカルファイル」を無効にし、両方を`file:///` URLで登録する必要があることを明記する。

originが異なるということは、localStorageの保存領域も分離される。これは標準的なオリジン分離からの帰結であり、実測はしていない。

そのため「ローカルファイル」を有効にした場合、controllerと通信できないことに加え、保存値が復元されない可能性がある。設定を途中で切り替えた場合、保存値が消えたように見える可能性もある。この点は未測定である。

## D-012: 通信前に技術スパイクを実施する

**状態:** 採用
**実施状況:** 実施済み

### 決定

本体へBroadcastChannelを組み込む前に、`spikes/broadcast-channel/`で独立した技術検証を行った。

### 理由

`file:` URLのoriginやOBSのCEF内での通信領域は、通常ブラウザと同じになる保証がなかったため。

本体へ組み込んでから通信不能が判明すると、不要なコードと設計変更が発生する。

### 却下した案

* 通常ブラウザで動いたことだけを根拠に本体へ実装する
* OBS上で動くと仮定してcontroller一式を先に作る

### 影響

技術的不確実性が高い機能は、今後も本体実装前のスパイクを検討する。

## D-013: controllerは状態の正本を持たない

**状態:** 採用

### 決定

controllerは、最後に表示側から受信したstateを画面へ表示するだけとする。

ボタン押下直後にcontroller側だけで値を増減しない。

### 理由

actionが不正、no-op、範囲上限、通信失敗等の場合、controllerが先行更新すると表示側と値が食い違うため。

正式な流れは次とする。

```text
controller操作
→ action送信
→ 表示側dispatch
→ state変更
→ state送信
→ controller表示更新
```

### 却下した案

* controllerで楽観的更新を行う
* controllerの値を定期的に表示側へ上書きする
* controllerにも独立したstate storeを持たせる

### 影響

操作後の表示更新は、表示側からstateが返信された後になる。

## D-014: controllerの状態表示は「接続済み」ではなく「同期済み」とする

**状態:** 採用

### 決定

controllerの状態は次の3種類とする。

* 未接続
* 同期待機
* 同期済み

「接続済み」という表現は使用しない。

### 理由

BroadcastChannelには、相手ページの存在や現在の生存状態を問い合わせる仕組みがない。

stateを一度受信しても、その後Browser Sourceが閉じられた可能性は検知できない。

そのため、「最後に有効なstateを受信した」という事実だけを示す「同期済み」が正確である。

### 却下した案

* BroadcastChannel生成成功だけで「接続済み」と表示する
* sync-request送信成功だけで「接続済み」と表示する

### 影響

controllerには最終同期時刻と再同期ボタンを表示する。

## D-015: heartbeatを実装しない

**状態:** 採用

### 決定

現行版では、表示ページとcontroller間のheartbeat、接続タイムアウト、切断検知を実装しない。

### 理由

heartbeatを導入する場合、単なる定期送信だけでなく、次の設計が必要になる。

* heartbeat送信間隔
* 応答タイムアウト
* ページ休止・バックグラウンド時のタイマー遅延
* OBSのシーン非表示時の挙動
* 誤検知からの復帰
* 複数ページ存在時の識別
* heartbeatと通常state通信の競合
* UI上の切断表示

現行の手動カウンターでは、接続状態をリアルタイムに保証する必要性が低い。

配信者は最終同期時刻と再同期ボタンで状態を確認できる。通信不能でも、表示側のウィジェットと保存済み状態は継続する。

実装コストと複雑性に対し、現段階で得られる価値が小さいと判断した。

### 却下した案

* 数秒ごとのping/pong
* stateを一定間隔で無条件送信する
* controllerから定期的にsync-requestを送る
* 一定時間stateが来なければ自動的に未接続へ戻す

### 将来再検討条件

次の場合はheartbeatまたは別の接続管理を再検討する。

* API自動取得を管理アプリが担う
* ローカルWebサーバーやWebSocketを採用する
* 接続断を利用者へ即時通知する必要が生じる
* 複数クライアントを正式対応する
* 操作要求に対する応答確認が必要になる

## D-016: 正式対応は表示ページ1つ、controller1つとする

**状態:** 採用

### 決定

現行版で正式対応する構成は次のとおりとする。

```text
表示ページ: 1つ
controller: 1つ
```

### 理由

BroadcastChannelは同じチャンネルを使用する全ページへメッセージを配信する。

表示ページが複数存在すると、次の問題が起きる。

* 1つのactionを全表示ページが受信する
* 各表示ページが独立したstateを更新する
* 各表示ページがそれぞれstateを返信する
* controllerには複数の競合するstateが届く
* ページ起動順や返信順によってcontroller表示が変わる
* どの表示ページを操作しているか判別できない

これを正式対応するには、少なくとも次が必要になる。

* widget instance ID
* controllerと表示ページのペアリング
* メッセージ送信先指定
* インスタンス一覧
* 重複ID検出
* 永続化キーとの対応
* 複数表示ページ用UI

現行製品の要件に対して過剰である。

### 却下した案

* 複数表示ページを暗黙に許可する
* 最後にstateを返信したページを正とみなす
* 全表示ページが同じ値なら問題ないものとして扱う
* controllerを複数表示ページへ無条件同期させる

### 将来再検討条件

複数の目標、複数配信画面、複数シーン別カウンターを正式機能にする場合は、instance IDとペアリング方式を含めて再設計する。

# 5. 永続化

## D-017: localStorageには`current`と`goal`だけを保存する

**状態:** 採用

### 決定

localStorageへ保存する実行時状態は次の2項目だけとする。

```text
current
goal
```

次は保存しない。

```text
label
message
achieved
theme
position
size
controllerの同期状態
最終同期時刻
```

### 理由

`current`と`goal`は、配信中にcontrollerから変更され、Browser Source更新やOBS再起動後にも維持する必要がある実行時データである。

一方、次の値は性質が異なる。

#### `label`と`message`

現行controllerでは実行時編集を行わない。

これらは`config.js`を設定上の正本とする方が、設定内容を把握しやすい。

localStorageへ保存すると、利用者が`config.js`を変更しても過去の保存値が優先され、変更が反映されない原因になる。

#### `theme`、`position`、`size`

これらは外観設定であり、現行では配信中に変更する実行時状態ではない。

`config.js`へ集約することで、配布ファイル上の設定と表示結果を一致させやすい。

#### `achieved`

`current >= goal`から導出できるため、独立保存すると矛盾を生じ得る。

#### controllerの同期状態・最終同期時刻

controllerを再読み込みすれば再評価すべき一時的なUI状態であり、再起動後に復元する意味がない。

### 却下した案

* state snapshot全体をそのままJSON保存する
* controller側のUI状態も保存する
* configとlocalStorageの両方に外観設定を保存する
* `achieved`を保存する

### 影響

localStorageの保存形式は次に限定される。

```json
{
  "version": 1,
  "current": 42,
  "goal": 100
}
```

## D-018: 永続化の正本は表示ページ側とする

**状態:** 採用

### 決定

localStorageへの保存と復元は`index.html`側で行う。

controllerは保存処理を担当しない。

### 理由

表示ページが実行時stateの正本であるため、永続化も同じ側へ配置する方が整合する。

controller側へ保存を持たせると、次の問題が起きる。

* controllerが閉じている間の変更を保存できない
* controller再読み込み時に古い値を表示側へ上書きする可能性
* 表示側とcontroller側で保存値が分裂する
* controllerなしでは永続化できなくなる

### 却下した案

* controllerのlocalStorageへ保存する
* 表示側とcontroller側の両方へ同じ値を保存する
* controllerが起動時に保存値を表示側へ送る

### 影響

controllerを閉じても表示と永続化は継続する。

---

## D-019: localStorageを選び、設定ファイルへの実行時書き込みは行わない

**状態:** 採用

### 決定

実行時状態の簡易保存にはlocalStorageを使用する。

`config.js`やJSONファイルへブラウザから直接書き込む方式は採用しない。

### 理由

通常のBrowser Source内JavaScriptは、任意のローカルファイルへ安全に書き込む機能を持たない。

設定ファイル書き込みを実現するには、次のいずれかが必要になる。

* デスクトップアプリ
* ローカルWebサーバー
* Node.js等の実行環境
* ブラウザ拡張
* 利用者による手動保存

現段階では構成が大きくなりすぎる。

localStorageなら、既存のHTML構成だけで、ページ更新やOBS再起動に対する簡易復元を実装できる。

### 却下した案

* `config.js`を実行時に書き換える
* 状態JSONファイルへ直接保存する
* ダウンロードファイルとして保存状態を出力する
* controllerのURLパラメータへ全状態を埋め込む

### 影響

保存機能はバックアップではなく、端末内の簡易復元と位置付ける。

OBSやブラウザのデータ削除によって消失する可能性がある。

## D-020: 保存キーには`index.html`のパスを含める

**状態:** 採用

### 決定

保存キーは概ね次の形式とする。

```text
obs-like-goal-widget-state-v1:<encodeURIComponent(location.pathname)>
```

### 理由

固定キーだけを使用すると、同じoriginとして扱われる別コピーのウィジェット間で状態が混ざる可能性がある。

パスを含めることで、別フォルダにコピーしたウィジェットを別インスタンスとして扱いやすくなる。

### 却下した案

* 全コピーで共通の固定キーを使う
* controllerのURLをキーにする
* ランダムIDを初回起動時に生成する
* `config.js`に利用者が手動でinstance IDを書く

### 影響

フォルダを移動またはコピーすると、保存値は原則として引き継がれない。

これは欠点ではなく、別ウィジェットとして分離するための意図した挙動である。

ただし、分離されるのは保存領域だけである。BroadcastChannelのチャンネル名は
`input-channel.js` と `controller.js` に固定値として持つため、コピー間で共有される。

2つのコピーを同時にOBSへ登録すると、利用者が意図せずD-016の非対応構成に入る。
controllerの操作が両方の表示ページへ届き、両方がstateを返信する。

READMEの「別の保存領域として扱われる」という記述が、コピー同士が完全に独立して
いるかのように読める点も、あわせて修正対象とする。

## D-021: 初回起動時にconfig初期値を自動保存しない

**状態:** 採用

### 決定

保存データが存在しない初回起動時は、`config.js`の値を表示するが、localStorageへ自動保存しない。

最初の実際の状態変更後から保存を開始する。

### 理由

起動直後にconfig値を保存すると、その後`config.js`の`current`や`goal`を変更しても、古いlocalStorage値が常に優先される。

保存値がない状態を「configを正として起動する状態」として維持することで、設定変更が自然に反映される。

### 却下した案

* 初回起動直後に必ずconfig値を保存する
* ページを開くたびにconfig値でlocalStorageを上書きする

### 影響

値を一度も変更していない利用者には、不要な保存キーが作成されない。

## D-022: `reset-counter`は0を保存する

**状態:** 採用

### 決定

`reset-counter`では、`current`だけを0へ戻し、現在の`goal`を維持して保存する。

### 理由

これは「保存状態を解除する操作」ではなく、「実行時カウンターを0から再開する操作」である。

再読み込みやOBS再起動後にも0から継続することが利用者の期待に合う。

### 却下した案

* `reset-counter`で保存キーを削除する
* `goal`もconfig初期値へ戻す
* 再読み込み後にreset前の値へ戻す

---

## D-023: `reset-all`は保存キーを削除する

**状態:** 採用

### 決定

`reset-all`では、実行時状態を起動時の検証済みconfig値へ戻し、localStorageの保存キーを削除する。

### 理由

`reset-all`は単なる数値変更ではなく、「保存値による上書きを解除し、configを再び正本に戻す操作」と位置付ける。

config初期値をlocalStorageへ再保存すると、後日configを変更しても古い値が優先される。

保存キー自体を削除することで、次回起動時にはその時点のconfig値が採用される。

### 却下した案

* config初期値をlocalStorageへ保存する
* currentだけを削除する
* reset-allでも通常の永続化購読に任せる

### 影響

reset-all後、次の通常状態変更から再び保存を開始する。

---

## D-024: 状態変化がなくても`reset-all`では保存キーを削除する

**状態:** 採用

### 決定

実行時状態がすでにconfig初期値と同じで、`store.dispatch()`が`false`を返す場合でも、正当な`reset-all`要求なら保存キーを削除する。

### 理由

次の状態があり得る。

1. 利用者が値を変更し、localStorageへ保存する。
2. 利用者が手動操作で、currentとgoalをconfig初期値と同じ値へ戻す。
3. 状態値はconfigと同じだが、保存キーは残っている。
4. `reset-all`を実行する。
5. 状態変化だけを条件にclearすると、保存キーが残る。

この状態では、後日config値を変更しても、古い保存値が優先され続ける。

したがって、状態変更の有無と、保存上書きを解除する操作は分けて扱う。

### 却下した案

* `dispatch()`が`true`のときだけclearする
* 状態がconfigと同じなら何もしない

### 影響

`dispatch()`の返り値は従来どおり状態変化の有無を示す。

保存キー削除の成否とは別である。

---

## D-025: localStorage異常時は永続化だけを無効化する

**状態:** 採用

### 決定

localStorageが未対応、アクセス拒否、容量不足、破損等の場合でも、表示、state、controller通信、手動操作は継続する。

### 理由

永続化は補助機能であり、表示ウィジェット全体を停止させる理由にはならない。

配信中に保存処理の失敗でウィジェットが消える方が影響が大きい。

### 却下した案

* localStorageが使えない場合は起動を中止する
* controllerを未接続扱いにする
* 画面全体へエラーを表示する
* 保存成功を状態変更の必須条件にする

### 影響

エラーは`console.error()`へ記録する。

利用者向けには「保存なしで動作する」と説明する。

# 6. 通信・保存のエラー処理

## D-026: 補助機能の失敗で表示本体を停止させない

**状態:** 採用

### 決定

次の機能でエラーが発生しても、可能な限り表示本体を継続する。

* BroadcastChannel生成
* 通信送信
* 通信購読者
* localStorage取得
* JSON解析
* 保存
* 保存データ削除

配信中のウィジェットでは、完全停止よりも機能縮退の方が望ましい。

例：

```text
通信失敗

→ 表示は継続

保存失敗
→ 再起動後の復元はできない
→ 現在の表示と操作は継続
```

### 却下した案

* いずれかの初期化失敗で例外をそのまま投げる
* 通信または保存に失敗したらページ全体をエラー表示へ切り替える

### 影響

各層で例外を捕捉し、責務外へ不要に伝播させない。

## D-027: 不正な保存データは採用しない

**状態:** 採用

### 決定

保存JSONは、version、current、goalを厳密に検証する。

不正な保存値は復元せず、可能であれば削除する。

### 理由

localStorageは外部からDevTools等で変更でき、過去バージョンや破損データが残る可能性もある。

不正値をstateへ渡すと、表示や進捗計算へ影響する。

### 却下した案

* `JSON.parse()`に成功すれば無条件採用する
* 数値文字列を保存データとして自動変換する
* version不一致でも可能な範囲で読み込む

### 影響

保存データは次を満たす必要がある。

* `version === 1`
* `current`が安全な範囲の整数
* `goal`が安全な範囲の整数

将来保存形式を変更する場合は、version migrationを別途設計する。

# 7. テストと変更管理

## D-028: 実装前に計画を確定し、実装後に実機試験してからコミットする

**状態:** 採用

### 決定

基本的な作業手順は次とする。

```text
1. 仕様・設計を検討
2. まず計画だけを作成
3. 計画をレビュー
4. 確定仕様を実装担当へ渡す
5. コミットせず実装
6. diffと実装報告を確認
7. ChromeとOBSで手動試験
8. 合格後にコミット
```

### 理由

OBS固有の挙動は、通常ブラウザや疑似試験だけでは確認できない場合がある。

実装とコミットを分けることで、不合格時に修正しやすくなる。

### 却下した案

* 実装担当に設計判断まで一括委任する
* 自動的にコミットまで行わせる
* 構文確認だけで完了とする

### 影響

Claude Codeには、明示しない限りコミットさせない。

---

## D-029: 現段階では自動テスト基盤を導入しない

**状態:** 採用

### 決定

現段階では、Node.jsや外部テストフレームワークを製品・リポジトリの必須要件として導入しない。

構文確認、疑似環境のスモークテスト、ChromeとOBSの手動試験を使用する。

### 理由

* 現在のコード規模では、テスト基盤導入の負担が相対的に大きい。
* OBS Browser SourceとCEF固有の挙動は、最終的に実機試験が必要である。
* Node.js等を導入しない現行方針を維持できる。
* 状態管理と描画を分離しているため、必要なロジック確認は限定的な疑似環境でも行える。

### 却下した案

* Jest、Vitest等を直ちに導入する
* Browser Sourceの実機試験を自動テストで完全代替する

### 却下範囲の限定

却下したのは外部テストフレームワークの導入であり、素のJavaScriptによる検証全般では
ない。Node.js・npm・ビルドを必要としない範囲（例：ブラウザで開くだけの検証ページから
`state.js` と `persistence.js` をアサーションする）は、D-001およびAGENTS.mdの制約に
抵触しないため、この決定の対象外とする。

### 将来再検討条件

次の場合は自動テスト基盤を再検討する。

* API連携が増える

# 9. 設定支援・管理アプリ

## D-032: 管理アプリをローカルWebサーバー方式へまだ固定しない

**状態:** 保留

### 決定

「管理アプリ」を開発する場合でも、現段階ではローカルWebサーバーを含む構成へ固定しない。

少なくとも次の2案を維持する。

### 案A: 設定支援クライアント

主な役割：

* `config.js`または設定JSONの安全な編集
* 入力検証
* プレビュー
* バックアップ
* 初期設定への復元
* file URL生成
* OBS用URLのコピー
* 必要ファイル・パスの診断

### 案B: 管理アプリ＋ローカルWebサーバー

主な役割：

* API取得
* 状態管理
* 保存
* ログ
* 障害復旧
* OBS表示ページ配信
* controllerとのリアルタイム通信

### 理由

両案では、製品の性質と運用負担が大きく異なる。

設定支援クライアントには次の利点がある。

* 常駐不要
* ポート競合なし
* ファイアウォール対応不要
* 現行構成を維持しやすい
* 配布・サポート負担が比較的小さい

ローカルWebサーバー方式には次の利点がある。

* APIキーをBrowser Sourceへ渡さずに済む
* API取得と状態管理を一元化できる
* OBS用URLを固定できる
* WebSocket等を利用できる
* 接続診断やログを実装しやすい

一方で、次の負担が増える。

* 常駐
* 二重起動
* ポート競合
* ファイアウォール
* セキュリティソフト
* 実行ファイル配布
* インストーラー
* アップデート
* サーバー停止時の影響

### 却下した案

* API仕様を確認する前にローカルサーバー方式を確定する
* 設定UIを作るなら必ず常駐アプリにする
* 現在のHTML構成を直ちに廃止する

### 判断時期

YouTube APIスパイクで、認証方式、取得頻度、秘密情報管理、実行主体の要件を確認した後に判断する。

# 10. API連携

## D-034: YouTube API連携前に独立した技術スパイクを行う

**状態:** 採用
**実施状況:** 未実施

### 決定

YouTube Data APIを本体へ組み込む前に、既存ウィジェットから独立したスパイクを実施する。

### 確認対象

* 配信URLから動画IDを抽出できるか
* 高評価数を取得できるか
* 同時視聴者数を取得できるか
* 配信前・配信中・終了後のレスポンス差
* 値が欠落・非公開の場合
* APIキー方式で必要機能が成立するか
* OAuthが必要になる範囲
* クォータ消費
* 現実的なポーリング間隔
* 403、404、クォータ超過、ネットワーク障害の分類
* 最後の正常値を維持するか
* 手動モードへどう切り替えるか
* file:// origin から `https://www.googleapis.com` へfetchできるか（CORS）
  - Browser Source内とカスタムブラウザドックの両方で、`location.origin` の実測値とあわせて記録する
  - 不可の場合、案Aはブラウザ内でのAPI自動取得を成立させられない
* 開発者のAPIキーを配布物へ同梱する方式が成立するか
  - クォータはGoogle Cloudプロジェクト単位であり、利用者間で共有される
  - 不成立の場合、利用者自身にキーを発行させる前提となり、D-033の設定支援の中身が変わる
* ポーリング主体を一意に決められるか
  - ドックを閉じた場合、シーン非表示でBrowser Sourceが停止した場合に取得が止まらないか
  - 複数ページが同時に取得した場合のクォータ倍化をどう防ぐか

### 実測済みの項目（2026-08-02）

確認対象のうち「file:// origin から `https://www.googleapis.com` へfetchできるか（CORS）」は測定を完了した。

環境（OBS 32.2.2.1 / Windows 11 25H2）:

* 通常ブラウザ（file URL）
* OBS カスタムブラウザドック
* OBS Browser Source 構成A（origin: `http://absolute`）
* OBS Browser Source 構成B（origin: `file://`）

いずれの環境でも結果は同一だった。

* 通常のfetch: `status=400`、`type=cors`、レスポンス本文の読み取りに成功
* `mode: "no-cors"` の対照リクエスト: `status=0`、`type=opaque`

無効なAPIキーを使用しているため400は想定内であり、**レスポンスを読み取れたこと自体がCORS通過の証拠**である。

読み取れた本文には `API key not valid. Please pass a valid API key.` を含むJSONが返っていた。エラー種別を判別できることを意味する。

OBS再起動後も結果は変化しなかった。

詳細な記録は `spikes/origin-fetch/README.md` §9 にある。

### この測定が確定させたこと

CORSはoriginに依存せず通過する。したがって次が成立する。

* OBS内のBrowser SourceおよびカスタムブラウザドックからYouTube Data APIを直接取得できる
* ローカルWebサーバーを立てる必要はない
* D-032のA案（設定支援クライアント）は技術的に成立する

A案とB案の選択は、技術的制約ではなく商品判断（APIキーの保管方法、常駐の要否、サポート範囲）に移った。

BroadcastChannelとAPI取得で、構成による可否が異なる点に注意する。

| 構成 | BroadcastChannel | API取得 |
| --- | --- | --- |
| 構成A（`http://absolute`） | 不可 | 可 |
| 構成B（`file://`） | 可 | 可 |

### 未測定のまま残る項目

確認対象のうち、次はまだ測定していない。

* 開発者のAPIキーを配布物へ同梱する方式が成立するか
* ポーリング主体を一意に決められるか
* 動画IDの抽出、高評価数と同時視聴者数の取得、配信前後のレスポンス差、クォータ消費、エラー分類

### 理由

API仕様と認証方式が、管理アプリの構成、秘密情報保存、常駐要否、ローカルサーバー要否を左右するため。

特に、file:// originからのfetch可否と、APIキーの配布方式が成立するかは、D-032の
A案とB案の選択を技術的に決定づける。この2点を確認する前にA/Bを固定してはならない。

### 却下した案

* API調査前にGUIや管理アプリを作る
* APIキーを`config.js`へ直接書くことを前提にする
* ローカルサーバーを先に実装する

## D-035: API取得層と表示stateの間に正規化境界を設ける

**状態:** 採用
**適用範囲:** 方針のみ確定。具体仕様は未確定

### 決定

将来のAPI取得値は、取得方式固有のレスポンスをそのままstateへ渡さず、正規化された外部データ形式を経由させる。

例：

```javascript
{
  source: "youtube",
  value: 123,
  fetchedAt: "2026-07-29T12:34:56+09:00",
  status: "ok",
  error: null
}
```

キー名を `current` ではなく `value` とするのは、API取得値が表示上の `current` に
そのまま入るとは限らないためである。手動補正との関係（§12）が未決定である以上、
状態名と同じキー名を使うと、決定前の前提を固定してしまう。

### 理由

API取得主体は将来、次のいずれになる可能性がある。

* Browser内JavaScript
* 設定支援クライアント
* 常駐管理アプリ
* ローカルWebサーバー

表示側のstateやrenderを取得方式から独立させることで、方式変更の影響を限定できる。

### 却下した案

* YouTube APIレスポンスをrender.jsで直接解釈する
* API取得コードからDOMを直接更新する
* API取得層がstate内部を直接変更する
